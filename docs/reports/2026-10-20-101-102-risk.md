# Risk review: plans 101 + 102 (Fable, 20 Oct, read-only)

## Summary
- Existing installs keep working if the build keeps: the customer manifest `id` `/<slug>`, `public/seller.webmanifest` unchanged (id `/seller`), and a **server-side** redirect (Worker 302) for every old `/o/<token>…` link. No reinstall needed; Android re-mints kitchen apps with the narrow scope on its own schedule.
- Old links (WhatsApp, delivered pushes, bookmarks) land on `/<slug>/o/<token>`. Printed label QR codes encode the order code, not a URL: safe.
- After Android re-mints an app, an **old** `/o/` link opens in Chrome instead of the app (works, not broken).
- My orders, customer settings, Remember me, seller passkeys: unchanged.
- Seller: the old "Seller" app keeps working if a page without `?k=` never links a per-kitchen manifest; 101 stage 4 must ship with stage 3 (shared Android session).
- Biggest risk: a manifest `start_url` outside the new scope (apps installed from an order page) → Chrome refuses; needs a unit test on every manifest.
- Kill switch: the scope value behind a Worker variable (default on); flip to `/` within a day if the tablet shows a URL bar inside the app.
- Rollback: Worker only, no migration; prefer the flag flip over a version rollback (links minted as `/<slug>/o/…` would 404 on 1.0.43).
- Recommendation: ship both with the safeguards, on a day with no open DellaVee menu; first live check on the Samsung tablet. Fallback: ship 101 + 102 routes/redirects with `scope: "/"` and narrow the scope in a later release.
