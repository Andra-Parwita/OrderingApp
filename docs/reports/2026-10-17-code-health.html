Code health report

Weekly food ordering app · 17 October 2026 · a read-only look at the code as it stands on the indra/brand_logo_ux branch, while three features are still being built.

In short

The app is in good shape. It is well organised, strict about types, tested against a real database, and the security basics are done properly. The weak spots are not bugs: they are repetition (the same little buttons, tags and sheets written again in many screens), the same data held in several places, and a handful of very large files that are getting hard to change safely.

Top five findings

  1. Nothing needs fixing urgently. No security hole was found; dependencies have no known vulnerabilities; the last full quality gate (14 Oct) was green with 2,199 unit tests and 81 end-to-end runs.
  2. The UI kit is under-used. There are about 1,400 one-off styles in screens against 85 in the shared kit: 116 hand-made buttons, 22 hand-made tags, 31 hand-made overlays and sheets, 33 hand-made notices. Five small shared components would absorb most of these.
  3. Orders and the current menu live in several places at once. The seller's orders are loaded by two parts of the app (Orders and Cook), each with its own live refresh; the current menu sits in four. It works, but every change touches two files, and two screens open means double the requests.
  4. Four files carry most of the server. One file routes all 110 server calls (1,698 lines) and three database files are 1,300 to 1,800 lines each. Fine for now; splitting them by area is the single best investment for the next year of changes.
  5. Two small privacy touch-ups keep the "no IP stored" promise literal: salt the short-lived IP hash used by two rate limiters, and add the standard browser security headers that are currently missing.

1. How the code is organised

Verdict: Good. Things are easy to find. The code is cut into clear layers, and a lint rule (an automatic checker) enforces the boundaries: screens of one feature may not reach into another feature, shared building blocks may not depend on screens, the browser app and the server never import each other, and loops of imports (A needs B needs A) are forbidden. The same checker forbids literal colours and pixel sizes in styles, so the theme stays the single source of truth.

2. State management

Verdict: OK, some duplication. The right tools are mostly in the right places: Redux (the app's shared memory) with sagas (the background workers that fetch and listen) for the big shared things like orders and menus; plain local state for forms; React context (a value handed down a screen tree) for the signed-in person and a few access flags. What is missing is a single, written rule for where data lives, so over time the same thing has been loaded in several places.

Where the same data lives twice

  • Seller orders: held by both the Orders slice and the Cook slice; each loads the list and each runs its own live loop. With Orders and Cook both open, every change is fetched twice.src/features/seller-orders/sellerOrdersSaga.ts:138 · src/features/seller-cook/cookSaga.ts:27 (both call fetchSellerOrders)
  • The current menu: in four slices (seller orders, menu, share, cook) and also fetched by settings. A live event refreshes only the one whose loop is running.
  • Customer menu: the basket's menu and the My orders page's per-kitchen menu cache are loaded separately, and both slices have an action with the same name.
  • The signed-in person: in a context for screens and in a module for sagas, kept in step by hand; a third signal says "signed out".src/app/session.tsx · src/api/device/sellerContext.ts · src/api/staffSignedOut.ts

The project's own architecture page already lists these honestly ("Things that look inconsistent"). This report agrees with it and adds the numbers.docs/architecture/state-and-data-flow.md §8

Live refresh: three ways of doing one thing

Keeping a screen up to date is done three ways: saga loops for Orders, Cook and Private; a hook for the Saturday screens (Sell, Hand over, Deliveries); and a separate connection plus a slow backup timer for customers. All three share the same back-off policy and the same "stop after 5 refusals" rule, which is good, but a change to that behaviour has to be made in three places.src/api/live.ts (saga loops) · src/features/seller-saturday/useLiveReload.ts · src/features/customer-orders/liveConnection.ts + orderPoll.ts

Is context used where Redux would be better, or the reverse?

No real misuse. Context is used for things that rarely change (who is signed in, "can this person see income"), which is what it is for. Redux holds the lists. The admin and sign-in areas skip Redux entirely and fetch on each screen; that is fine while each piece of data is shown on one screen only.

Most valuable improvements

  1. One source for the kitchen's orders. Let Cook read from the Orders slice (or a shared "kitchen data" slice) and drop its own fetch and live loop. Halves the requests when both are open. Size M.
  2. One current-menu slice that the other slices read from. Size M.
  3. One live-refresh helper used by both sagas and hooks, so the back-off and "stop after 5" rules exist once. Size M.
  4. Write the rule down: "shown on two or more screens → Redux; one screen → a hook that calls the API". Then move the three or four helpers that broke it as they come up. Size S each.
  5. One holder for the signed-in person, with the context fed from the module rather than two writes. Size S.
