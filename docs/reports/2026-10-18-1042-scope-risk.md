# Can 101, 102, 104 rows and the button rule go into 1.0.42? (risk and impact)

**Asked by the owner, 18 Oct:** "investigate the risk/impact of 101 and 102 and 104 for this release and also about the buttons-two-lines rule, since ideally I want to add them all in this 1.0.42 release." Read-only; no app source changed. Live is **1.0.41**. Builder hours are the plans' own estimates; at this project's real pace (live-status) builders usually finish in a quarter to a half of that.

## Recommendation (short)

1. **1.0.42 as planned + the two low-risk extras:** 104 delivery rows (once the owner picks A or B) and the button rule on the **three phone toolbars only** (done after builders 3a and 3c finish, because they are editing two of those toolbars right now).
2. **Do the 102 "phone proof" now, on the live app** (no code needed, about 20 minutes on an Android phone). It decides what 101 and 102 build.
3. **1.0.43 = 102 stages 1–3 without the scope change + 101 stages 1–5**, one builder for both (they edit the same three files), after the proof and after 1.0.42 has been on the phones a few days.
4. **1.0.44 = 102 scope + routes (stages 4–6) together.** The scope change must never ship alone: it would put My orders, Settings and every order page into a browser tab inside every installed kitchen app (see 102 below).
5. Why not all in 1.0.42: it is already the biggest release so far (118 files, +12,870/−10,594 lines since v1.0.41, plus three builders still writing, plus 098 stage 3, 106 and 107 not designed yet). 101 and 102 change the **identity of installed apps**, which a redeploy of 1.0.41 cannot undo on the phones, and both need a real-phone proof that most likely needs a deployed URL (marked "unconfirmed" below).

## Release size

- 1.0.42 today: 118 source files changed since v1.0.41 (098 splits, 100, 103 fixes 1–6, 104), three builders in flight (105 adds a server route; 103 fixes 7–8; 104 extras), then 098 stage 3, 106 and 107 (no mock-up yet). Screens that change for a seller: Orders (header, Active tab, print choice, edit any order, Paid sheet), Cook (phone), Menu (edit session, Sell button), Labels, rail/More; for a customer: the passkey message. The live check after deploy already covers 7 seller screens + a customer order end to end.
- Adding 101 + 102 (0–3) puts ~35 more files and the two **identity** changes (seller app id, customer manifest/icon/install button) into the same evening; 102 routes adds ~20 more and every link.
- With everything in, the owner's after-deploy check grows from ~20 minutes to a few hours across two phones and a tablet, and a problem found at 23:00 in the install flow cannot be separated from a problem in Orders.

## If the owner still wants all of it in 1.0.42: minimum safety steps

1. Do the **102 stage 0 proof on live first** (20 min); if scope is not the cause, drop the scope change for good.
2. **No scope change without the routes** (102 stages 1 and 4–6 ship together or not at all).
3. 101: pages loaded **without `?k=` keep the default "Seller" manifest link** (never swap the manifest inside the old installed app); stage 4 (own-kitchen memory on Android) ships with stage 3, never later.
4. One builder for `kitchenManifest.ts`, `kitchenHeadLinks.ts`, `manifestLinks.ts`; 101 and 102 in sequence, not in a wave.
5. New e2e before the gate: `/o/<token>`, `/my-orders`, `/settings` redirects (3), `multi-seller` with `?k=`, `seller-auth` signed out with `k`; then the **full** gate, one run at a time.
6. Deploy on a day with no open menu; owner's Android and iPhone at hand; keep `v1.0.41` ready to redeploy (no migration, so no D1 restore is needed; a backup anyway costs nothing). Install on the **owner's** phone first; send the beta "reset / reinstall" text only after that works.
7. Feature flags: the codebase has no switch mechanism; a `wrangler.jsonc` var read by `buildManifest`/`kitchenPage` could turn the per-kitchen seller head and the scope on or off per deploy, but a flag cannot un-mint an app Chrome has already updated, so it only helps for the page side.

## Couldn't confirm

- Whether Android Chrome makes a real WebAPK (not a plain shortcut) for the LAN dev server with the mkcert certificate. If it cannot, every Android proof (101 stage 0, 102 after-deploy checks) needs a deployed URL, and plan 048's "the per-kitchen seller manifest was not installable on Android Chrome" may have had this cause rather than a manifest fault.
- Chrome's behaviour when a page inside an installed app links a manifest with a **different** `id` (101 stage 2 as written).
- The exact delay before an installed app picks up a scope or name change (Chrome's own schedule; "days" in the plans).
- 101 stage 6 (push links to a seller with `?k=`): today `worker/push/dispatch.ts` sends only customer URLs (`/o/<token>`); no seller push URL exists, so the stage is probably empty.
- Playwright cannot emulate Android's font-size +1; the 360 px capture is an approximation of the Samsung case.
