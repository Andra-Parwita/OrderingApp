# 073 · Fewer, bigger requests (audit of every place the app talks to the server)

**Status:** approved (2026-10-14, owner: "add them now"). The Sell/Deliveries timers, the customer order poll, per-navigation customer reloads and event-aware live loaders are done by [plan 074](074-live-updates-everywhere.md); this plan does the rest: (1) the menu wizard re-reads only what an op changed (no 7-GET refresh), (2) the seller's per-page `useNotPublished` menu fetch reuses loaded data, (3) short TTL caches for settings/preferences (`useSellerLanguages`, IncomeAccessProvider, preferences), (4) Cook "made" ± and Pack ticks saved in one go (reusing plan 072's auto-save), (5) the admin page's one request per kitchen becomes one request (Worker change). Items 1–3 now; 4–5 after plan 074 part A (shared files).
**Owner's words (2026-10-13):** "do an audit for similar things like the tick (each tick in the menu Dishes step sent a full request and greyed the boxes; now being fixed by plan 072 = debounced single save) in other areas, including the customer app, i.e. don't send requests to the server too often or too granular where we can avoid it."
**Goal:** the app asks the server only when something really changed or the person really needs fresh data: taps that can be grouped are grouped, data that was just loaded is not loaded again, and nothing polls while the screen is hidden. No change in what people see, except screens that feel quicker and the server/phone doing less.

Scope: everything in `src/` that calls `src/api` (sagas, hooks, components, timers). Plan 072's Dishes and Check steps are **not** repeated here. "Requests" = HTTP calls; numbers are counted from the code, not measured on a phone.
