# Lessons

Each entry opens with the "do this instead", then what happened and what it cost (conventions §7).

1. **Check weekdays against a real calendar before putting sample dates in a brief.** The coordinator wrote "Sat 11 Oct / Fri 10 Oct 2026" into four wireframe briefs and the mock fixture; in 2026 Saturday is the 10th. A builder caught it in stage 3.2; cost one fix round, and the wireframes still carry the wrong dates.
2. **Read the PC clock (`date`) before writing any time on the board.** Phase 2 and stage 3.0 times were estimated and ran ahead of the real clock by up to ~40 min; corrected and noted on the board. Cost: board credibility, two correction passes. **Repeated on 9 Oct 04:46–05:12** (D-044, 6.3, 6.4 rows) — run `date` in the same call that writes the time, every time.
3. **When a brief restricts what a folder may import, think about every future user of that folder.** The 3.1 brief said `src/harness` may import only `ui`/`theme`; feature harnesses in wave 2 then failed lint, and one builder suppressed the rule. Cost: one fix round plus removing a suppression.
4. **Have the haiku reader extract a large owner source once, then reconcile it against the decisions before building.** Done right for the owner's "Delave" prototype (484-line extract, one reconciliation table, one ruling, D-027) — kept the 150 KB page out of every brief.
5. **Run the contrast check on any palette before adopting it, even the owner's own.** The reference palette had three AA gaps (sage text, gold text, input borders); fixed by adding tokens, not changing the look.
6. **After a bug-fix deviation in a builder report, ask for (or check) a test that fails without the fix.** 3.5 fixed a basket→order redirect bug (`placeReset`) without proof that its test fails without the fix. Not yet verified.
7. **Forbid `git stash` / `checkout` / `reset` in builder briefs on this PC.** `core.autocrlf=true` rewrites files with CRLF on checkout; the 4.1 builder stashed to compare a build and left 26 files with CRLF, failing Prettier at the gate although its report said format passed. Cost: a failed gate and a normalisation pass.
8. **Check what the public API returns against the visibility rulings, not just the screens.** The customer screens hid chef names (D-012), but `GET /api/menu` still sent them. Found by reading the contract before wave 2.
9. **Keep e2e specs off limited stock.** One Playwright run shares one mock store across all projects; specs that ordered the 20-portion Lemper sold it out, and a later spec failed "randomly" three times before the coordinator traced it. Use unlimited items; test limits in one serial spec that reads the current remaining first. **Correction (23:28):** it wasn't the cause of this flake — read the failure's page snapshot (`error-context.md`) before naming a root cause.
10. **A flaky e2e test can be a real bug: find the mechanism before fixing.** The New-order flake was the seller layout remounting when a media query flipped (Playwright's full-page screenshot briefly reports a 1×1 viewport) — the same thing a tablet rotation would do to a real seller's half-typed order. Found with a probe logging resize/media events; fixed by keeping one stable layout tree. Cost: two rounds, one on a wrong hypothesis.
11. **Never run `python - <<'X'` heredocs on this PC; check for stray processes before every gate.** The Windows Store Python launcher sometimes never sees end-of-input and spins at 100% CPU. Eight such processes ran for up to 6 hours; the coordinator blamed webkit and test load for hangs and timeouts instead of checking the machine — the owner noticed the CPU. Use the Edit tool or Node scripts; add "no stdin-waiting or background commands; stop every process you start" to every brief. **Follow-up (9 Oct, 7.1 and 7.3):** two builders still ran `python -` despite the rule in capitals (both caught and stopped it themselves). Writing the rule isn't enough — briefs should also say *what to use instead* ("edit files only with the Write/Edit tools; for scripts use `node -e` or a `.mjs` file in scratch/").12. **When two builders run in parallel, don't let both run Playwright: one e2e owner per wave, or the coordinator gates.** In the 8.2/8.3 fix round (9 Oct 17:28) both were told to run e2e; both used port 5181 and one waited twice for the other's server. No harm, but runs could have collided and reported false failures. Conventions §4 already says this; the coordinator's briefs broke it.
13. **Test sign-in with two roles in one browser.** The admin and seller passkeys shared one stored id per site; setting up a seller on the owner's PC locked the admin out (9 Oct ~18:50). Every test used one role per browser. Cost: an owner lockout and a fix round.
14. **Briefs say what not to run and what not to format.** The 8.4b builder ran `pnpm format` across the whole repo, touching files it didn't own. Nothing changed by luck. Briefs now say: format only the files you changed; no full Playwright suite.
15. **Smoke-load and look at each changed screen before calling a visible change done (conventions §5).** Phase 4 and the Switch person round were reported as green from tests only: "Live" dot, admin and seller sign-in messages, Switch person in the rail and More tab. Captures are owed.
16. **Build sample data from the clock, never from fixed dates.** The sample kitchens' week was hard-coded (cook Sat 10 Oct, cut-off Fri 9 Oct 21:00 Melbourne). At midnight on 10 Oct every fresh test database became "orders closed", and about 8 browser specs failed in plan 003's gate for a reason unrelated to the work. Seeds now take `now` (comingSaturday). Date helpers must use the cook's zone, not UTC: the same night showed "My orders" grouping by UTC midnight.
17. **Builders must report a hung process honestly, and the coordinator checks for stray processes after every builder.** Plan 001 fixer B ran `python3 -` once (lesson 11). It said it stopped it, but the process kept spinning at 100% CPU from 03:55 to 04:20, until the coordinator's stray check after the wave found and stopped it. Briefs already forbid heredocs and python, yet four of the plan 001 builders used heredocs anyway, so the stray check after each report is the guard that works.
18. **Edit docs with a `.mjs` script written by the Write tool, or the Edit tool; never `sed` or `printf` with backticks.** In GNU sed, `` \` `` means "start of buffer/line", so `s/\`/`/g` put a backtick at the start of every line of plan 004 (10 Oct, 05:49). `printf '…\`…'` in single quotes also writes the backslash literally. Both were undone at once, but `docs/` edits are the coordinator's and must be exact.
19. **In a parallel wave, only one builder may run Playwright, even the design-compare check; or the coordinator runs it after the wave.** On 10 Oct (06:08, 06:24, 06:45) the coordinator's own briefs told the plan 004 builder to run the compare spec while a fix-plan builder worked on the server. They didn't collide, because the other builder only ran Vitest, but it broke conventions §4 ("in a parallel wave, builders don't run the end-to-end suite"), the same slip as lesson 12. Also: briefs said "no heredocs" and still saw node and shell heredocs in 5 of 9 rounds. The stray-process check after each report caught nothing left running, but the rule needs restating as "Edit and Write tools only" in every brief, which the later briefs did.
20. **One Playwright run at a time, and run one spec as `playwright test <file> --project=<project> --no-deps`.** On 11 Oct the coordinator's briefs let three builders run Playwright in the same wave (lesson 19 again). The plan 029 builder ran `playwright test day-selling --workers=1`, which matched nothing narrow enough and, with the projects' dependencies, ran the whole 85-test suite on one worker for over 30 minutes. It held the one e2e server (port 5181, `scratch/e2e-d1`), so the plan 038 builder's admin spec failed twice ("not freshly seeded", then EBUSY) and its screenshots waited. Also found: a capture spec that calls `/api/dev/reset` and a spec that changes a demo kitchen's stock would break other specs in a parallel run. Now: builders don't run Playwright in a wave; the coordinator runs specs one at a time with `--project … --no-deps`; any spec that resets or changes shared data goes in a sequential project (or uses its own kitchen) before the parallel gate.
21. **Stop processes by the exact PID you started, never by a name or command-line pattern.** On 11 Oct (19:57) the coordinator stopped an e2e run by killing every node process whose command line matched `playwright|5181|e2e-d1`; that also killed the session's Playwright MCP browser tool (`@playwright/mcp`), which stayed disconnected for the rest of the session. Conventions §6 already says "by PID, never by name": list the run's own processes (its port's listener and its children) and stop only those.
22. **Don't run the full e2e suite at the same time as the full unit run.** On 12 Oct (21:26) the owner asked to run them in parallel to save time; the e2e run then failed 8 tests, 4 of them only because the busy PC made the Vite dev server fail ("fetch failed", a `vite-error-overlay` over the page), and 6 unit tests timed out. All passed alone. Saving 10 minutes cost a 35-minute fixer round. Now: unit first, then e2e (or e2e on a quiet PC); if the owner asks for both at once, say the trade-off first.
23. **A full e2e run can hang for hours if the PC sleeps.** On 12–13 Oct the overnight run sat in `design-compare-customer` for 6.4 hours (the owner's PC slept); it passed alone at once in the morning. Now: before an unattended run, keep the PC awake (Windows power setting or `powercfg /requestsoverride`), or run the slow design-compare specs separately; read the run's duration before trusting its result.
24. **A builder killed every node process again (13 Oct, 06:50) after a lint run hung**: lesson 21 says stop processes by the exact PID only. It stopped the local dev server too. Briefs must restate: "never kill processes by name; if a command hangs, stop only its own PID and report".
25. **A spec run without `--no-deps` on a project with dependencies runs the whole suite** (14 Oct, 06:50): plan 073's builder ran `seller-menu.spec.ts --project=settings-desktop-chromium` without `--no-deps`; Playwright first ran every MAIN project against code two other builders were changing, failed widely, held the e2e server, and its permission to stop its own PID was denied. The coordinator stopped exactly that process tree by PID. Every brief already says `--no-deps --workers=1`; the builder must copy the command exactly.
26. **Start long runs only with the tool's background mode (`run_in_background`), never with a shell `&`; before re-running, list the processes to see whether the first run is still alive.** On 17 Oct (19:08) the coordinator started the 1.0.38 gate with `{ …; } &` inside a normal Bash call. Its log looked empty, so it started the gate again properly; the first run was in fact still running, and the two runs collided on `scratch/d1-tests` and `scratch/e2e-d1`: 82 unit files and the whole e2e run failed (`ERR_RUNTIME_FAILURE`, `EBUSY`). The coordinator stopped exactly the first run's process tree by PID (lesson 21), cleared the scratch databases and re-ran. Cost: about 15 minutes and a wasted 13-minute unit run.
27. **Never `git commit -a` while a builder is editing the tree, and never commit or push without the owner's say-so for that step.** On 17 Oct the coordinator committed a plan-doc line with `git commit -qam`, which swept a builder's half-finished plan 081 server code into a pushed commit; the branch referenced files that weren't committed until the next commit. The owner then ruled: no git writes unless asked, ask first every time. Stage only the files you changed, by path.
28. **Give every estimate with its start time, and write the actual next to it.** The owner asked on 17 Oct for estimate-vs-actual on every step ("so we can better estimate later on"). Builders are usually far faster than the coordinator's estimates (e.g. plan 081 stages: estimates 60–75 min, actual 15–21 min), while gates and fix rounds run at or above the estimate. Keep the table in `docs/plans/live-status.md`, with clock times from `date`.
29. **Sample data and research must be Australian (AUD, Adelaide) unless the owner says otherwise.** On 17 Oct agents drew Rupiah prices, Bali/Jakarta addresses and UK/European shop links in three mock-ups and one research answer; the owner corrected it each time ("we used only AUD", "we are in Adelaide, Australia, not UK"). Every mock-up and research brief now says "AUD and Adelaide only", and the coordinator checks for "Rp" before showing the owner.
30. **This PC's `python - <<EOF` heredocs worked all of 17 Oct, but lesson 11 still applies: check for stray `python` processes after a session that used them.** The coordinator used Python heredocs for doc edits dozens of times on 17 Oct; a stray-process check found none spinning. Prefer the Edit tool for docs anyway.
31. **Draw pictures that stay on screen across pages in a persistent parent, never inside a keyed page transition, and test that the `<img>` is the same element after navigating.** The customer pages slide in with `<Slide key={pathname}>`, which remounted each page's kitchen banner; on iPhone a fresh `<img>` paints blank first, so the banner flashed on every page change (owner, 17-18 Oct). Fixed in 093 (shell banner) and 094 (banner on every customer page, no small logo bar); the seller layout had the same pattern (banner unmounted on task screens / outside the Orders list). Cost: two hotfix releases (1.0.40, 1.0.41). Applies to plan 082 (store).
32. **Test anything that touches the page head or scripts under the production Content-Security-Policy, not only the dev server.** On 20 Oct plan 115's builder put the splash logic in inline `<script>`s; every test passed because dev mode allows `'unsafe-inline'`, but live (`script-src 'self' 'nonce-…'`) would have blocked it and the splash would have covered the app forever. Caught in review by reading `worker/securityHeaders.ts`. Now: the script lives in `public/splash.js`, a CSS fallback hides the splash once `#root` renders, and `mocks/indexHtmlCsp.test.ts` fails on any inline script or `on*` handler.
33. **Global styles in `index.html` must not set anything the app sets itself (`color-scheme`, fonts, theme).** The splash's `:root { color-scheme: light }` stayed in the page after the splash was gone and outranked the app's setting, so choosing Dark in Settings no longer applied (found by `native-customer.spec.ts`, 21 Oct). Keep first-paint CSS to the splash's own variables.
34. **A failure that repeats in two full runs is a real signal even if the spec passes alone: investigate it, don't label it "load flake".** On 21 Oct three specs failed twice after the hotfix. The coordinator first suspected the new request time limits; the investigation proved otherwise (no aborted requests, the service worker inactive in e2e): the hotfix added page-heavy specs, every page load got slower under the parallel suite (about 680 dev modules per page), and tight 30 s test limits plus a one-slot toast race in the seller app failed. Fixed in the specs. Each fix then uncovered the next failure, because a failing main project skips its dependent projects: keep going until a full run is 0 failed.
35. **A global change in the network layer (timeouts, retries, service-worker strategy) needs a full-suite run and a normal-network test, not just its own unit tests.** Each plan 114 builder ran only scoped tests; the side effects (dark mode, slow saves, timing) showed only when everything ran together. The owner asked for a "normal network" check (one request, no re-send, no waiting on the slow-link timer); keep that test.
36. **Anything that can stop a customer from ordering must fail open, and gets an adversarial review.** The first `clientOrderId` version could return a cancelled order and refused malformed ids (both would lose a sale). Rule from the owner: "a lost sale is worse than a duplicate". Fix: only a live, uncancelled menu order is returned; any problem places the order; an off switch (`ORDER_DEDUPE`); Fable tried to break it before release.
37. **Don't assert wall-clock times in e2e under a parallel suite; assert the mechanism.** The "menu under 4 s" check failed at 5.7 s under load; it now reads the browser's own request timings to prove the 4.5 s service-worker timer wasn't used.
38. **Lesson 26 again: the coordinator started a gate with a shell `&` on 20 Oct (H1) and lost its notification.** Use `run_in_background` every time.
39. **Measure before fixing a speed problem; the obvious suspect is often wrong.** On 24 Oct the coordinator blamed the menu pictures (`decoding="sync"`, hotfix 1.0.43.1) for the slow cold start and proposed placeholder boxes. A 15-minute Playwright measurement (iPhone-sized Chrome, ×4 CPU, Fast 4G, 3 runs, picture decoding switched by intercepting the bundle) showed no difference at all; the real cost was the 1.86 MB JavaScript bundle (about 1 s between the splash and the menu). Measure first, with the slow-phone profile, then plan.
40. **Know what each audience downloads: check the bundle by area.** Since the start every customer downloaded the whole app, seller and admin screens and all their texts (1.86 MB, of which customer screens were 158 KB); nobody looked because the app "worked". Plan 119 split it (customer part about 1 MB, staff part loaded only on `/seller` and `/admin`) and added `pnpm run check:bundle`, which fails if seller or admin code is back in the customer entry. Run it in every gate and before every deploy.
41. **Before rolling back a "slower" release, rule out the test network (VPN, weak signal).** On 24 Oct hotfix 1.0.43.2 was rolled back because the iPhone showed a long black screen; the owner was on a VPN. Redeployed minutes later, the check passed. Ask "VPN or Wi-Fi?" before a rollback for speed; the first open after a deploy also re-downloads everything (cache version change), so judge from the 2nd and 3rd open.
42. **iOS shows its own black launch screen before any page code runs; only `apple-touch-startup-image` links (exact device size, portrait) replace it.** The splash and the saved page cannot cover that first moment. Hotfix 1.0.43.3 added one ShaggyBobo launch picture set for iPhone 14 and newer (light and dark); other devices keep the black screen. Android needs nothing: Chrome builds a splash from the manifest colour and icon.
43. **A test that mixes a fixed fixture date with the real clock is a time bomb: freeze the clock (`vi.setSystemTime`) or make fixture dates relative to now.** On 24 Oct two tests started failing on their own: `editSession.test.tsx` (the fixture's cooking date became "today", a Saturday) and `liveConnection.test.tsx` (a fixed 14 Oct order fell out of the 10-day My orders window under `useRealTimers`). Both looked like regressions from the day's work and cost a debugging round each.
44. **iOS reads the launch picture (and title and icon) from the page on screen at the moment of "Add to Home Screen", and our service worker may show a saved older page first.** On 24 Oct the owner re-added DellaVee right after hotfix 1.0.43.3 and still got a black start, even after swipe-up cold starts: Safari had shown the saved pre-hotfix copy (no launch-picture links). Removing the app, refreshing the page once in Safari and adding it again fixed it. Tell customers: refresh once, then add; existing installs must be removed and added again to get a new launch picture.
45. **On iOS 26 the system blurs and dims page content right under the status bar in a home-screen web app; no CSS turns it off, and a PC browser never shows it.** On 25 Oct the tall DellaVee banner (plan 123) looked blurred behind the clock at rest and sharp when pulled down, even after hotfix 1.0.44.2 removed our only fixed layer at the top. It matches iOS 26's "scroll edge effect" (Liquid Glass), which native apps can switch off per scroll view but web pages cannot. Check status-bar looks on a real iOS 26 iPhone before promising "sharp"; the owner liked the soft look and kept it (no setting). With Settings → Accessibility → Display & Text Size → Reduce Transparency on, iOS makes the status bar area opaque instead (owner checked, 25 Oct).
