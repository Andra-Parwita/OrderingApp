# Store apps: one ShaggyBobo app (web shell, React Native or native)

**Status: parked (owner, 24 Oct, D-118):** "We will do just website in near future, most important is customer don't get confused if sent different link for different kitchen." Kept as background for later.

**Analysis only (Fable, 2026-10-24; owner asked 24 Oct: "The app could be just one ShaggyBobo, and inside can have invitation to seller, or customer can also select which kitchen etc."). No code was changed. Rulings go to [decisions](../decisions/README.md); the build, if any, starts as a plan ([D-055](../decisions/README.md)).**

## Summary

1. **One ShaggyBobo app for everyone is the right shape for the stores.** Apple's own rule 4.2.6 names it ("a single binary to host all client content in a picker model"), and rule 4.3(a) rejects one app per kitchen. Kitchens stay invite-only; the picker lists the kitchens this phone has opened.
2. **Pick A (a shell of the live website), Android first.** A Trusted Web Activity from Bubblewrap costs about A$36 once, 12–20 hours of work and a 14-day closed test, and it fixes the Samsung install confusion at its root (one Play install, no Chrome menus). The web app stays the product.
3. **iPhone stays a Home Screen web app for now.** An iPhone shell costs A$149 a year, needs native push (APNs or FCM) on the Worker and carries a real Apple 4.2 "repackaged website" risk. Revisit it with v1.1.0.
4. **B (React Native) only if v1.1.0 (payments, events, store) needs it;** it is a second client to keep current (80–150 h for the customer side alone, 20–40 h a year). **C (native Kotlin and Swift) is out:** two more codebases and no Mac.
5. **1.0.44 stays as built and is deployed first.** The per-kitchen routes `/<slug>/o/<token>` are exactly what a one-app picker and deep links need; the per-kitchen seller apps are paused as a direction (not removed), the store app would carry the kitchen switcher instead.

Money is in AUD at about 1.43 AUD per USD (mid-2026 rate, [Pluang, 22 Jul 2026](https://pluang.com/en/tools/currency-converter/usd-aud)). Hours are coordinator plus AI builders, with the gate; the owner's device checks are extra.

## 2 · The three ways to build it

Baseline: today's PWA (per-kitchen manifests, plan 068; web push, plan 004; saved page at once, plan 115; passkeys on `order.shaggybobo.app`; 1.0.44 adds kitchen-scoped routes, one seller app per kitchen and one "Install app" button, D-117).

### A · App shell of the website

**Android:** a Trusted Web Activity (TWA) built with [Bubblewrap](https://github.com/GoogleChromeLabs/bubblewrap) (latest release v1.27.0, 9 Oct; Node 18+; it downloads its own JDK and Android SDK, so it runs on Windows) or PWABuilder. The app is Chrome showing the live site full-screen with no URL bar once `/.well-known/assetlinks.json` names the app's signing key ([PWABuilder next steps](https://github.com/pwa-builder/CloudAPK/blob/master/Next-steps-unsigned.md)). Everything the PWA does keeps working because it **is** Chrome: web push, passkeys, cookies, the service worker, the saved page.

**iPhone:** a small Swift app with a WKWebView that loads the live site. Capacitor's `server.url` does this too, but its docs say it "is intended for use with live-reload servers" and "is not intended for use in production" ([Capacitor config](https://capacitorjs.com/docs/config)), and a bundled Capacitor build runs at a `capacitor://localhost` origin that breaks our same-origin cookies, CSP and passkey RP ID. So the iPhone shell is hand-written: WKWebView, Universal Links, a push bridge (APNs token → our Worker), the `webcredentials` associated domain so the site's passkeys work inside the view.

### B · React Native (Expo)

A second client, written in TypeScript, reusing `shared/` (types, API contracts, order codes, zones, i18n JSON) but **none of the React DOM screens, styled-components or the service worker**. Expo's EAS builds iOS in the cloud: the Free plan has 15 Android and 15 iOS builds, EAS Submit to both stores and one concurrent macOS job; Starter is US$19 a month, Production US$199 a month ([Expo pricing](https://expo.dev/pricing), fetched 24 Oct 2026; a cached copy said US$99: check before paying).

### C · Fully native (Kotlin and Swift)

Two more codebases, nothing shared but the API. Same server changes as B. Effort 400–800 h first build, 60–100 h a year; Swift needs Xcode, so a cloud Mac for every compile and no way for the owner or builders to see the iPhone app except TestFlight. Apple approval is the easiest of the three; nothing else is. **Not a fit** for one seller, 10–50 orders and "keep it simple".

## 5 · Recommendation

- **A. Web shell, Android first:** a Play Store "ShaggyBobo" TWA plus the web picker and invites; iPhone stays a Home Screen web app until v1.1.0. Consequence: the stores are solved where they hurt (Samsung) for A$36 and 12–20 h; iPhone users keep today's experience.
- **B. React Native customer app:** store presence on both platforms with native polish. Consequence: a second client at 80–150 h plus 20–40 h a year, and every feature ships twice.
- **C. Native Kotlin and Swift:** the best store fit. Consequence: 400–800 h, three codebases and a Mac.

**Pick: A, Android first.** It keeps "keep it simple" true: one codebase, the web stays the product, the stores become one more way in. The iPhone shell is a separate yes-or-no later, because it alone brings the yearly fee, native push on the Worker and the 4.2 risk.
